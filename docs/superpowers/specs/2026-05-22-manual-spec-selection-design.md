# Manual spec selection for the APIM UI integration pipeline

**Date:** 2026-05-22
**Status:** Approved — ready for implementation planning

## Problem

The Jenkins job `apim-4.7.0-ui-integration-staging-testgrid-pipeline` always runs
the full Cypress UI suite on its first pass. There is no way for the person
triggering a build to scope the run to a subset of specs. The only existing
"run a subset" behaviour is the automatic **rerun** pass: after the full first
pass, `test.sh` rereads the specs that failed (`cypress/failed-specs.txt`) and
retries only those.

We want to give that same targeting power to the user up front, at the
"Build with Parameters" screen.

## Goal

Add an **optional** job parameter that lets the user list the specs to run.

- Parameter set → only those specs run on the first pass.
- Parameter blank → full suite runs, exactly as today.

## Current flow (for reference)

```
Jenkins job  ──runs──▶  main.groovy  (testgrid-jenkins-library, branch test-4.7.0)
                            │
                            ▼
                  scripts/test-deployment.sh   (4 positional args)
                            │
                            ▼
        product repo  tests/test.sh   (support-apim-apps, branch support-9.3.194.x-full)
                            │
                  first pass:  NO_COLOR=1 npm run test     (== cypress run --e2e, full suite)
                            │
                  after:run hook writes cypress/failed-specs.txt
                            │
                  rerun pass:  npx cypress run --e2e --spec "$FAILED_SPECS"
```

Spec paths are relative to the `tests/` directory, e.g.
`cypress/e2e/publisher/foo.cy.js` — the same format `failed-specs.txt` uses and
the same format Cypress `--spec` expects.

## Approach

**Chosen: Approach A — new positional argument.**

Plumb the spec list as a new positional CLI argument through
`main.groovy` → `test-deployment.sh` → `test.sh`. This matches the repo's
stated pipeline-to-shell contract ("positional CLI args plus the shared
`parameters.json`"); `test-deployment.sh` already takes 4 positional args, so a
5th is a consistent, minimal change.

Rejected: routing through `parameters.json`. That store is for secrets and
deployment properties surfaced via `get_prop`/`deployment.properties`, which is
generated by the CFN deploy scripts. `test_specs` is a plain build input, not a
deployment property — that path would be indirect and overkill.

## Changes

### 1. Jenkins job parameter

Added to the job config XML (not stored in any repo), applied with
`jenkins-cli update-job`.

- Type: `hudson.model.TextParameterDefinition` (multi-line text box).
- Name: `test_specs`.
- Default value: empty.
- Description: explains that the user enters **one spec path or glob per line**,
  relative to the `tests/` directory
  (e.g. `cypress/e2e/publisher/**/*.cy.js`), and that leaving it blank runs the
  full suite.
- Placed last in the parameter list, after `use_staging`, as an optional input.

### 2. `main.groovy` (testgrid-jenkins-library, branch `test-4.7.0`)

- Add a script-level variable `def testSpecs = ""` alongside the existing
  top-level `def deploymentDirectories = []` etc.
- In the *Constructing parameter files* stage `script` block, normalize the
  multi-line parameter into one comma-separated string:

  ```groovy
  testSpecs = (params.test_specs ?: '').readLines()
                  .collect { it.trim() }
                  .findAll { it }
                  .join(',')
  ```

  Use `params.test_specs` (the params map), **not** a bare global — `main.groovy`
  is shared by other jobs that do not declare this parameter, and `params`
  returns `null` for an undeclared key instead of throwing.
- In `create_build_jobs`, pass `testSpecs` as a quoted 5th argument to
  `test-deployment.sh`:

  ```
  ./scripts/test-deployment.sh <deploymentDirectory> ${product_repository} \
      ${product_test_branch} ${product_test_script} "<testSpecs>"
  ```

  `testSpecs` is injected into the `sh` script literally (the pattern already
  used for `updateType`). The normalized value has no newlines; spec
  paths/globs contain no spaces.

### 3. `scripts/test-deployment.sh` (testgrid-jenkins-library, branch `test-4.7.0`)

- Read a 5th positional arg: `testSpecs=$5`.
- Forward it to `test.sh` via a new long option:

  ```
  source .../test.sh --input-dir "..." --output-dir "..." --test-specs "${testSpecs}"
  ```

  The flag is always passed; an empty value is handled by `test.sh`.

### 4. `tests/test.sh` (support-apim-apps, branch `support-9.3.194.x-full`)

- Add a `test-specs)` case to the existing `getopts` long-option handler
  (the `-)` branch), storing the value in `TEST_SPECS`.
- Replace the first-pass invocation:

  ```bash
  # before
  NO_COLOR=1 npm run test
  MVNSTATE_FIRST=$?

  # after
  if [ -n "$TEST_SPECS" ]; then
      echo "===== Running user-selected specs only ====="
      NO_COLOR=1 npx cypress run --e2e --spec "$TEST_SPECS"
  else
      NO_COLOR=1 npm run test
  fi
  MVNSTATE_FIRST=$?
  ```

`npm run test` is `cypress run --e2e`, so the targeted form is consistent with
the full-suite form and with the existing rerun command.

> Scope note: the `apim-apps` (`main` branch) copy of `test.sh` is **not**
> changed in this iteration — only the `support-9.3.194.x-full` branch the job
> actually checks out. Mirroring to `apim-apps` is deferred.

## Unchanged behaviour

- **Rerun pass.** The `after:run` hook in `cypress.config.js` still writes
  `failed-specs.txt` regardless of how the first pass was scoped. If a
  user-selected spec fails, the existing rerun retries exactly that failing
  subset. No change to rerun code.
- **Flaky reporting.** `flaky-specs.txt` and the build-email flaky section work
  unchanged.
- **Full-suite builds.** With `test_specs` blank, the pipeline behaves bit-for-bit
  as it does today.

## Error handling

No pre-validation of the entered paths. A typo'd path or a glob that matches
nothing makes Cypress fail fast with "Can't run because no spec files were
found", surfaced normally as a build failure. This is called out in the
parameter description so users know the expected format.

## Verification

Pipeline code only executes inside a Jenkins build, so validation is two real
test builds of the job:

1. `test_specs` set to one small known spec — confirm only that spec runs on the
   first pass.
2. `test_specs` blank — confirm the full suite runs (no regression).
